title: "Server Messages"
description: "The message types competitors should handle after connecting over WebSocket."
---

These are the main message types a competitor client should expect from the server.

## `heartbeat`

```json
{"type":"heartbeat"}
```

## `authenticated`

```json
{
  "type": "authenticated",
  "trader_id": "9d64e278-8b56-46e9-9cab-18c5b22f2fb9",
  "username": "team-alpha"
}
```

## `snapshot`

```json
{
  "type": "snapshot",
  "channel": "l3",
  "market": "BTC-USD",
  "sequence": 0,
  "bids": [
    { "price": 100, "quantity": 12 },
    { "price": 99, "quantity": 8 }
  ],
  "asks": [
    { "price": 101, "quantity": 6 },
    { "price": 102, "quantity": 10 }
  ]
}
```

Even though `channel` is `l3`, `bids` and `asks` are aggregated price levels, not per-order rows.

## `delta`

```json
{
  "type": "delta",
  "channel": "l3",
  "market": "BTC-USD",
  "sequence": 1,
  "events": [
    {
      "kind": "level_updated",
      "side": "BUY",
      "price": 100,
      "quantity": 14
    },
    {
      "kind": "trade",
      "price": 101,
      "quantity": 1
    }
  ]
}
```

`level_updated` sets the full visible quantity for one side and one price. `quantity: 0` means remove that level from your local book. These are price-level updates, not per-order add, amend, or remove events.

## `fill`

```json
{
  "type": "fill",
  "fill": {
    "fill_id": "fef1b4fd-d0b0-4270-8831-b4c51aa43f1d",
    "market": "BTC-USD",
    "maker_order_id": "4d6c28f4-b349-4a4d-8927-8141c36eb6eb",
    "taker_order_id": "66377526-7b98-485a-8c40-7024e68fa3c5",
    "price": 100,
    "quantity": 1,
    "occurred_at": "2026-03-18T15:28:04.132958Z"
  }
}
```

## `order_state`

```json
{
  "type": "order_state",
  "order": {
    "id": "66377526-7b98-485a-8c40-7024e68fa3c5",
    "trader_id": "9d64e278-8b56-46e9-9cab-18c5b22f2fb9",
    "market": "BTC-USD",
    "side": "BUY",
    "price": 100,
    "quantity": 2,
    "remaining": 1,
    "created_at": "2026-03-18T15:28:01.342510Z"
  },
  "status": "open"
}
```

`status` is one of:

- `open`
- `filled`
- `canceled`

Use `order_state` for your own exact resting-order detail. This is the per-order account feed; the market-data `snapshot` and `delta` messages are intentionally aggregated.

For market orders, accepted taker flow is terminal. You should expect `status: "filled"` with `remaining: 0` because market orders never rest on the book. In that case, `order.price` is the weighted average executed price across the immediate fills, rounded down to an integer.

## `admin_message`

```json
{
  "type": "admin_message",
  "message": {
    "message_id": "26aa26f5-8d20-4a6c-9b66-99549585036f",
    "target_username": null,
    "target_trader_id": null,
    "market": "BTC-USD",
    "level": "info",
    "title": "Desk notice",
    "body": "Trading will stop in five minutes.",
    "created_at": "2026-03-18T16:05:00.000000Z"
  }
}
```

Competitors should treat this as operator guidance that may affect trading behavior, such as desk notices, trading halts, or settlement announcements.

## `resync_required`

```json
{
  "type": "resync_required",
  "channel": "l3",
  "market": "BTC-USD",
  "expected_sequence": 5,
  "current_sequence": 9,
  "reason": "market data lagged by 3 messages; resubscribe for a fresh snapshot"
}
```

Use [Recovery and resync](/reference/recovery-and-resync) for the recommended client response.

## Required handling

- `heartbeat` means the connection is still alive.
- `snapshot` and `delta` are the market-data source of truth while the subscription is healthy.
- `fill` and `order_state` are the user-scoped state feed after authentication.
- `admin_message` can change the practical trading environment even before you refresh REST state.
- `resync_required` means your local state is no longer trustworthy and must be rebuilt.
