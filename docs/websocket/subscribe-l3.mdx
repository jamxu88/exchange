---
title: "Subscribe"
description: "Subscribe to one sequenced market-data stream on the socket."
---

Use `subscribe` to receive a fresh aggregated snapshot and then sequenced price-level deltas for one market.

The channel name is `l3`, but the payload is aggregated price-level book data, not a public per-order L3 feed.

<RequestExample>

```json Client Message
{"op":"subscribe","channel":"l3","market":"BTC-USD","last_sequence":null}
```

</RequestExample>

<ResponseExample>

```json First Response
{
  "type": "snapshot",
  "channel": "l3",
  "market": "BTC-USD",
  "sequence": 0,
  "bids": [
    { "price": 100, "quantity": 12 },
    { "price": 99, "quantity": 8 }
  ],
  "asks": [
    { "price": 101, "quantity": 6 },
    { "price": 102, "quantity": 10 }
  ]
}
```

</ResponseExample>

## Client fields

- `op` must be `subscribe`.
- `channel` must be `l3`.
- `l3` is the current market-data channel name, even though the book payload is aggregated by price level.
- `market` is the market you want to subscribe to.
- `last_sequence` is part of the message shape, but the supported recovery flow still expects a fresh resubscribe after a gap.

## What happens next

- The server first sends a `snapshot`.
- `bids` and `asks` in that snapshot are aggregated price levels, not raw order rows.
- After the snapshot, the server sends `delta` messages with contiguous `start_sequence` to `sequence` ranges.
- The exchange currently derives browser-facing market data from the canonical order-event stream, batches those price-level updates per market, and flushes them roughly every `100ms`, so one `delta` can carry several ordered events.
- A `level_updated` delta sets the total visible quantity for one side and one price.
- Those deltas are price-level updates, not per-order add, amend, or remove events.
- `quantity: 0` means that price level should be removed from your local book.
- `trade` deltas carry executed price and quantity only.
- If the backend detects a gap or a lagged receiver, it sends `resync_required`.

## Notes

- The current implementation supports one `l3` market subscription per connection.
- If you need multiple markets, open multiple sockets.
- Use `start_sequence` to validate the first event in a batched `delta`, then store `sequence` as your new last applied market sequence.
- Use `order_state` messages for your own exact resting-order state. The `l3` market-data stream is intentionally aggregated.
