## REST error shape

REST errors deliver a single `error` field so your client can surface what went wrong:

```json
{
  "error": "human readable message"
}
```

## REST status mapping

Handle these statuses explicitly in your error UI:

| Status | What it means for you |
| --- | --- |
| `400` | Bad payload: wrong market, price, tick-size, quantity, amend, or market order liquidity |
| `401` | Missing or invalid API key |
| `429` | Authenticated rate limit bucket (`500 ops per 10s` by default) exceeded |
| `403` | Resource exists but belongs to another competitor |
| `404` | Order, market, or user not found |
| `409` | Trade would breach limits, market status blocks trading, or duplicate username |
| `500` | Unexpected overflow or backend failure |

Use [Rate limits](/reference/rate-limits) for the exact shared-bucket behavior behind `429`.

## WebSocket `error` messages

These tell you about protocol-level problems you need to fix before trading.

Known codes you may see:

- `invalid_message`
- `unsupported_channel`
- `invalid_api_key`

Example:

```json
{
  "type": "error",
  "code": "unsupported_channel",
  "message": "supported market-data channels are l2 and l3"
}
```

## WebSocket `reject` messages

Trading operations fail with a `reject`. Handle every code so you stay in sync with the exchange.

Known codes:

- `unauthenticated`
- `trading_disabled`
- `invalid_market`
- `market_not_configured`
- `market_disabled`
- `market_settled`
- `invalid_price`
- `price_too_large`
- `tick_size_violation`
- `no_liquidity`
- `invalid_quantity`
- `quantity_too_large`
- `quantity_below_minimum`
- `invalid_remaining`
- `invalid_amend`
- `order_not_found`
- `order_not_owned`
- `position_limit_exceeded`
- `rate_limit_exceeded`
- `overflow`

Example:

```json
{
  "type": "reject",
  "op": "submit_order",
  "request_id": "req-1",
  "code": "position_limit_exceeded",
  "message": "projected net position for BTC-USD would be 1005; limit is +/-1000"
}
```

## Health degradation

Check `GET /health` to monitor persistence:

- `status: "ok"` when persistence is `disabled` or `ok`
- `status: "degraded"` when persistence is `retrying`, `backpressured`, or `stopped`

Internal operator-only error cases are intentionally not expanded here.
