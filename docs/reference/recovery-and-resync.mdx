## Market-data sequencing

Every market-data delta carries a per-market sequence range.

Here’s how the flow works:

- A fresh `subscribe` sends a snapshot.
- `l2` snapshots rebuild your aggregated price-level book state.
- `l3_snapshot` rebuilds your raw per-order public book state.
- Each `delta` or `l3_delta` includes `start_sequence` for the first event in the batch and `sequence` for the last event in the batch.
- Deltas arrive in contiguous sequence order, even when the server batches several events into one frame.
- The server emits `resync_required` whenever it detects a gap.
- The same message fires when your broadcast receiver lags behind.

## Client action for market-data resync

When this message hits you:

```json
{
  "type": "resync_required",
  "channel": "l2",
  "market": "BTC-USD",
  "expected_sequence": 5,
  "current_sequence": 9,
  "reason": "market sequence gap detected; resubscribe for a fresh snapshot"
}
```

Do this:

1. compare your local last-applied sequence for that market against `expected_sequence` from the `resync_required` message (and treat any gap the server reports as authoritative)
2. discard your local book state for that market
3. send a new `subscribe` for the same channel and market
4. replace local state with the returned `snapshot` or `l3_snapshot`
5. resume processing `delta` / `l3_delta` batches using the new snapshot’s `sequence` as your baseline

## User-event lag

When the user event stream lags, you get:

```json
{
  "type": "resync_required",
  "channel": "user",
  "market": null,
  "expected_sequence": null,
  "current_sequence": null,
  "reason": "user event stream lagged by N messages; refresh account state and reconnect if needed"
}
```

Do this:

1. re-fetch `/api/v1/user`
2. re-fetch `/api/v1/positions`
3. re-fetch `/api/v1/balance`
4. re-fetch `/api/v1/open-orders`
5. re-fetch `/api/v1/fills`
6. reconnect the socket if your client cannot confidently recover local order state

## Market-metadata lag

When the market-metadata stream lags, you may get:

```json
{
  "type": "resync_required",
  "channel": "markets",
  "market": null,
  "expected_sequence": null,
  "current_sequence": null,
  "reason": "market event stream lagged by N messages; refresh market state from REST if needed"
}
```

Do this:

1. re-fetch `/api/v1/markets`
2. replace your cached market definitions
3. keep using websocket `market_state` pushes after the refresh

## Restart behavior

After a backend restart, the process reloads the JSON checkpoint (when configured) for users, markets, balances, positions, and related metadata. **Resting open orders are not included in that checkpoint**, so the in-memory order books start empty and any previous resting orders are gone from the exchange’s view.

- Positions and balances restored from the checkpoint remain queryable over REST.
- Market-data sequences are rebuilt from the live engine state (empty books until new orders arrive).
- No historical market-data or user-event replay is available.

Treat a reconnect after restart as a fresh session: re-fetch [open orders](/rest/open-orders), [portfolio](/rest/portfolio), and [markets](/rest/markets) over REST before trusting cached client state.

## Current recovery boundary

What you can rely on:

- Checkpoint restore for users, markets, balances, and positions (when `CHECKPOINT_PATH` is set and a file exists).
- Market-data gap and lag detection via `resync_required`.
- User-event and market-metadata lag detection via `resync_required`.

Still missing:

- Durable restore of resting open orders across process restarts.
- Full settlement replay.
- Durable sequence continuation across restarts.
- Historical gap-fill API.
