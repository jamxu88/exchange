## Market-data sequencing

Every market-data delta carries a per-market sequence range.

Here’s how the flow works:

- A fresh `subscribe` sends a snapshot.
- `l2` snapshots rebuild your aggregated price-level book state.
- `l3_snapshot` rebuilds your raw per-order public book state.
- Each `delta` or `l3_delta` includes `start_sequence` for the first event in the batch and `sequence` for the last event in the batch.
- Deltas arrive in contiguous sequence order, even when the server batches several events into one frame.
- The server emits `resync_required` whenever it detects a gap.
- The same message fires when your broadcast receiver lags behind.

## Client action for market-data resync

When this message hits you:

```json
{
  "type": "resync_required",
  "channel": "l2",
  "market": "BTC-USD",
  "expected_sequence": 5,
  "current_sequence": 9,
  "reason": "market sequence gap detected; resubscribe for a fresh snapshot"
}
```

Do this:

1. treat `start_sequence` as the first sequence number you expect for the next batch
2. if `start_sequence` is not exactly your expected next sequence, discard your local book for that market
3. send a new `subscribe`
4. replace local state with the returned `snapshot` or `l3_snapshot`
5. resume processing deltas from the new snapshot sequence

## User-event lag

When the user event stream lags, you get:

```json
{
  "type": "resync_required",
  "channel": "user",
  "market": null,
  "expected_sequence": null,
  "current_sequence": null,
  "reason": "user event stream lagged by N messages; refresh account state and reconnect if needed"
}
```

Do this:

1. re-fetch `/api/v1/user`
2. re-fetch `/api/v1/positions`
3. re-fetch `/api/v1/open-orders`
4. re-fetch `/api/v1/fills`
5. reconnect the socket if your client cannot confidently recover local order state

## Restart behavior

After a backend restart:

- Open orders are restored into the in-memory books from storage.
- Persisted positions remain queryable.
- Market-data sequences restart from the rebuilt derived state for each market.
- No historical replay is available.

Treat a reconnect after restart as a fresh session and re-bootstrap account state over REST before trusting cached data.

## Current recovery boundary

What you can rely on:

- Open-order recovery into the in-memory book.
- Persisted position reads after restart.
- Market-data gap detection.
- User-event lag detection.

Still missing:

- Full settlement replay.
- Durable sequence continuation.
- Historical gap-fill API.
