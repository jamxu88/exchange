This documentation describes the exchange exactly as it exists today: a Rust backend in `exchange/`, a Next.js client in `client/`, and a single EC2 deployment with local PostgreSQL for an internal competition.

## Current live endpoints

- HTTPS: `https://exchange.jamesxu.dev`
- Health: `https://exchange.jamesxu.dev/health`
- Swagger UI: `https://exchange.jamesxu.dev/docs`
- WebSocket: `wss://exchange.jamesxu.dev/ws`

## What this system is

- Internal competition exchange, not a public product
- Operator-provisioned users only
- Assigned API key per participant
- In-memory matching engine and orderbooks
- Local PostgreSQL for durable user, exchange-control, position, order, fill, message, and audit state
- Background batched persistence writer so the matching path does not write directly to PostgreSQL

## What this system is not

- No public self-registration
- No JWT, OAuth, or browser-style public auth model
- No multi-node matching cluster
- No durable replay log for market data
- No full replay-based settlement recovery on restart yet

## Important current caveats

- The ECS client stack is live behind the ALB test host `http://exchange-client-alb-1466111370.us-east-2.elb.amazonaws.com`.
- Final HTTPS on `exchange.jamesxu.dev` is waiting on ACM DNS validation and external DNS cutover.
- The exchange backend origin now listens on `0.0.0.0:8080` on the EC2 host so the ALB target group can reach it.
- Startup recovery rebuilds in-memory orderbooks from persisted open orders and keeps persisted positions queryable, but it does not yet replay full settlement history.
- Sequence numbers are per-market and in-memory; they reset on process restart.
- The EC2 host currently pulls from GitHub using a temporary stored PAT. Replace that with a deploy key or machine-user SSH key and revoke the PAT.
