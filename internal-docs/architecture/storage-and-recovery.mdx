## Storage modes

The backend supports two storage backends:

- `in_memory`
- `postgres`

`in_memory` is still the default local mode.

The deployed EC2 host should run with:

```text
STORAGE_BACKEND=postgres
```

## PostgreSQL write model

The PostgreSQL backend does not write directly on the hot matching path.

Instead it:

1. keeps an in-memory cache for reads
2. enqueues durable mutations to a bounded queue
3. flushes batches on a dedicated background writer thread
4. retries failed batches in order
5. reports queue and flush health through `/health`

Config knobs:

- `POSTGRES_WRITE_BATCH_SIZE`
- `POSTGRES_WRITE_FLUSH_INTERVAL_MS`
- `POSTGRES_WRITE_QUEUE_CAPACITY`
- `POSTGRES_WRITE_RETRY_BACKOFF_MS`

## Startup recovery

On process start, the backend:

1. reads persisted open orders from the repository
2. rebuilds in-memory orderbooks
3. serves position, fill, and order queries from the storage-backed cache
4. starts serving traffic with those restored books

This means resting orders survive a process restart if they were already flushed to PostgreSQL, and user positions remain queryable after the process comes back.

## What recovery does not do yet

- no full replay-based settlement recovery
- no historical recomputation of positions and PnL from an event journal alone
- no durable continuation of market-data sequence numbers
- no crash guarantee for writes still queued but not flushed

## Operational meaning

Today, restart recovery is good enough to restore live resting orders into the book and keep persisted positions available, but it is not yet a complete replay-driven engine-state recovery system.
